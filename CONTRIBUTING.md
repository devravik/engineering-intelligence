# Contributing to Engineering Intelligence

Thank you for your interest in contributing to **Engineering Intelligence**!

Our mission is to equip AI coding agents with a senior engineer's reasoning layer—ensuring software generated by AI is deliberate, simple, maintainable, and free of AI slop.

Whether you are improving an existing command, reporting an anti-pattern, submitting a framework adapter, or expanding documentation, we welcome your contributions.

---

## Areas Where We Need Help

### 1. Framework & Ecosystem Adapters
In Phase 6 of our roadmap, we are building specialized intelligence adapters for major web stacks:
* **Laravel / PHP:** Eloquent N+1 detection, policy enforcement, FormRequest validation.
* **Next.js / React:** Server Action boundaries, RSC payload bloat, Suspense fallback hygiene.
* **Go:** Goroutine lifecycle leaks, context propagation, error wrapping conventions.
* **Python / Django / FastAPI:** Pydantic validation boundaries, queryset evaluation, async loop blocking.
* **Databases:** PostgreSQL / MySQL migration lock hazards, unindexed foreign keys.

### 2. Anti-Slop Heuristic Catalog
Help us expand our catalog of detectable AI slop:
* Single-implementation interfaces and redundant abstract factories.
* Gratuitous wrappers around ORMs or HTTP clients.
* Tautological echo comments.
* Speculative generic type gymnastics.

### 3. Real-World Benchmarks
Contribute synthetic test cases and benchmark repositories with planted architectural defects to help us evaluate agent detection accuracy.

## Development & Contribution Workflow

### 1. Fork and Clone
```bash
git clone https://github.com/devravik/engineering-intelligence.git
cd engineering-intelligence
```

### 2. Propose or Discuss
For significant changes or new command ideas, please open a GitHub Discussion or Issue first to align on philosophy and approach.

### 3. Authoring Guidelines
* **Evidence Before Judgment:** Recommendations and heuristics must be grounded in physical codebase evidence (git diff, symbol lookups, test outputs).
* **High Signal-to-Noise:** Avoid generating generic checklists. All findings must follow the [Standard Finding Schema](docs/commands/overview.md#the-standard-finding-format).
* **Local-First:** Never introduce dependencies on external cloud APIs or third-party web services.

### 4. Submitting a Pull Request
1. Create a feature branch (`git checkout -b feature/framework-adapter`).
2. Make your edits to `SKILL.md`, `docs/`, or `templates/`.
3. Ensure formatting and markdown links are valid.
4. Push your branch and open a Pull Request with a clear description of the problem solved.
